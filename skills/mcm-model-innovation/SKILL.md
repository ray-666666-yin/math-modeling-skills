# 面向证据的模型改进

把“希望有创新”变成一个可检验问题：现有方案在哪种条件下有什么不足，改变哪项结构能够解决它。合理结论也可以是保留基线、先补验证或暂不增加复杂度。

## 定位改进对象

读本题要求、现有模型和与本次改进相关的结果。记录需要保留的目标、硬约束、输出口径及前后问接口。已有报告可直接利用，不要求先运行另一套技能。

从具体证据找瓶颈，例如：边界附近的系统残差、遗漏的机制、参数不可辨识、对任意假设过度敏感、约束不满足，或计算量使要求无法完成。尚无数据或运行记录时，把瓶颈写成待检验假说，不描述成已发现事实。

先区分三类工作：纠正题意或实现错误、提高已有方案质量、提出可能具有文献新颖性的做法。第一类应先修正；第三类需要额外查证，不能仅依据本次对话宣称原创算法。

## 提出能落地的改动

围绕瓶颈选择少量有实质区别的候选。按需查看 [改进与比较设计](references/improvement-design.md)。每个保留方案写清：

1. 原模型中要变更的具体关系、假设、判据、约束表达或计算步骤。
2. 新的数学定义、变量含义、参数来源、所需数据及与既有模块的接口。
3. 预期起作用的机制，以及新增假设可能失效的条件。
4. 验证收益的评价量、基线、实验设计和额外计算成本。
5. 什么证据会让团队放弃改进，以及可继续交付的基础方案。

保留题面硬约束。若确有需要讨论放宽约束的情景，应独立命名并解释其与原任务的差异，不能把扩大可行域的收益混称为同条件提升。新增惩罚项也需检查实际约束违反量。

比较方案时先看数据是否支持新增自由度，再看收益是否覆盖复杂度与时间成本。未知参数没有依据时，先提出标定或辨识计划；不能用“增加自适应模块”等名称代替定义。

## 将贡献主张与证据对应

比较时固定能够固定的题意、数据、硬约束、评价口径和精度要求。预算或模型条件不同的比较应说明差异，并报告性能与计算成本的权衡。

新增多个模块时，用必要的消融或替代对照识别贡献；随机方法要考虑波动，参数扰动要有依据。可用的检查包括独立回算约束、合成数据参数回收、留出评估、离散加密、边界测试和失效情景。选择真正检验主张的项目，不机械套固定次数或百分比。

尚未执行时只交付实验计划和预期方向；已执行时报告真实结果及局限。没有差距证书或适用证明时，不能把多次搜索结果相近写成全局最优。拟合改善也不自动证明机制正确或外部有效。

## 交付

先说明最值得改的部分与理由，再给可实施定义、比较设计和停止条件。若用户要论文表述，将贡献限定在已有证据内，例如“在相同约束下减少某类误差”，而不是无依据的“首次提出”或“全面优于”。

只要求思路时直接回答；要求落地时沿用项目现有文件组织和已授权范围。本技能不自动重写全题、不改变无关模型，也不要求安装其他技能。
